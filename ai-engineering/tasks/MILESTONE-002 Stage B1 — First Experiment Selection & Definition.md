# 3. First Experiment Selection Principle

The first experiment must be based on:

```text
Real Engineering Work
```

Do NOT create:

```text
Synthetic Task

Artificial Demo

Toy Revision

Task created only to prove the asset useful
```

The experiment candidate must originate from a genuine engineering need.

Possible sources include:

```text
Current repository work

A real repository inconsistency

A genuine review finding

A real engineering revision

A legitimate architecture correction
```

However:

```text
Potential Issue
≠
Automatically Eligible Experiment
```

The task must pass the Stage A eligibility model.

---

# 4. Repository Inspection for Candidate Task

Inspect the current repository state.

Identify whether there is a genuine engineering task that could require:

```text
Targeted Engineering Revision
```

Possible evidence sources:

```text
Existing review findings

Known inconsistencies

Architecture observations

Documentation mismatches

Incomplete bounded work

Clearly identified revision needs
```

Do NOT manufacture findings.

Do NOT intentionally introduce defects.

Do NOT treat:

```text
“we need an experiment”
```

as sufficient justification for a revision.

The revision task must independently deserve to exist.

---

# 5. Candidate Task Discovery

Document all realistic candidate tasks discovered.

For each candidate, record conceptually:

```text
Candidate Task

Why the task exists independently

Current evidence

Potential relevance to CANDIDATE-001

Observable outcome

Potential risks
```

Do not create a long inventory merely for completeness.

Prefer:

```text
Small
High-Quality Candidate Set
```

If only one genuine candidate exists:

```text
One Candidate
is sufficient.
```

If no genuine candidate exists:

```text
NO_ELIGIBLE_TASK
```

is an acceptable outcome.

Do NOT force an experiment.

---

# 6. Experiment Eligibility Assessment

Evaluate each candidate using the Stage A framework.

Assess:

```text
Task Authenticity

Asset Relevance

Meaningful Complexity

Observable Outcome

Context Suitability

Potential Context Variation

Repeatability Potential
```

Also evaluate disqualifiers:

```text
Task Too Trivial

No Clear Revision Need

No Meaningful Asset Responsibility

No Observable Outcome

Artificial Motivation

Excessive Dependency on Other Assets
```

Avoid scoring systems.

Use:

```text
Evidence-Based Qualitative Assessment
```

---

# 7. Candidate-001 Responsibility Match

For a candidate task to qualify, it should naturally involve:

```text
A Known Engineering Target
+
A Bounded Revision Need
+
An Existing Context
+
A Need to Perform Focused Revision
```

It should NOT primarily require:

```text
Open Exploration

Initial Problem Discovery

Repository-Wide Inspection

Task Boundary Negotiation

Full Task Closeout
```

Those responsibilities belong outside the core responsibility of CANDIDATE-001.

Important:

```text
CANDIDATE-001
is not a general engineering execution process.
```

It is:

```text
Targeted Engineering Revision
```

---

# 8. Single Asset Experiment Boundary

The first experiment should focus on:

```text
Primary Validation Subject

CANDIDATE-001
```

Other normal engineering activities may occur.

For example:

```text
Git Inspection

Tests

Diff Review

Repository Validation
```

may still be used as ordinary engineering practice.

However:

```text
Do NOT evaluate those activities
as separate asset experiments.
```

Specifically:

```text
CANDIDATE-002
must NOT be treated
as a co-primary validation subject
in Stage B1.
```

This preserves:

```text
Attribution Clarity
```

# 10. Invocation Boundary

Define exactly what Stage B2 will validate.

Example conceptual boundary:

```text
Input:
Known revision target
+
Existing context
+
Revision objective

↓

CANDIDATE-001 Experimental Procedure

↓

Focused Revision Guidance

↓

Engineering Work

↓

Observed Evidence
```

Do NOT expand the experiment into:

```text
Full Engineering Lifecycle
```

The experiment should validate the smallest meaningful responsibility.

---

# 11. Expected Value Hypothesis

For the first experiment, explicitly state:

```text
What value is expected?
```

Examples:

```text
Clearer revision reasoning

Reduced unnecessary scope expansion

Better alignment between finding and revision

Improved change traceability

Lower repeated correction
```

However:

```text
Expected Value
≠
Success Criteria
```

The hypothesis must remain falsifiable.

The experiment must be allowed to show:

```text
No Meaningful Value
```

---

# 12. Evidence Capture Plan

Define what evidence Stage B2 and B3 should capture.

Possible evidence:

```text
Original Engineering Context

Revision Target

Invocation Record

Actual Revision Process

Resulting Changes

Human Intervention

Observed Benefits

Observed Problems

Unexpected Behavior

Process Overhead

Non-Use / Boundary Notes
```

Do not define excessive documentation requirements.

The experiment should not become:

```text
More expensive than the engineering task itself.
```

---

# 13. Potential Failure Signals

Define potential failure indicators before the experiment.

Possible examples:

```text
Revision scope remains unclear

Repeated human boundary correction

Output duplicates normal reasoning

No measurable or observable value

Process overhead exceeds benefit

Asset responsibility overlaps another activity

Invocation requires excessive context

The task turns out not to be a suitable experiment
```

Important:

```text
Failure Signals
are pre-commitments to observe honestly.
```

Do not redefine failure after the experiment to preserve a success narrative.

---

# 14. Process Overhead Hypothesis

Before Stage B2, estimate likely overhead qualitatively.

Consider:

```text
Additional reasoning

Additional documentation

Context preparation

Human clarification

Additional review steps
```

The purpose is not to calculate:

```text
ROI
```

or:

```text
Performance Score
```

The purpose is to ensure:

```text
Validation Process
does not dominate
Engineering Work.
```
